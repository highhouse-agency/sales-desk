# Undo in this conversation

## Keep a receipt before saving

For the last approved preview only, keep the operator, source/operation keys, appended row IDs, each changed cell's before/after value, and the actual verified Calendar event before/after contents. Include linked workflow payloads, task close fields, Pipeline fields and Review resolution metadata. Keep these receipts in the conversation, never in a new sheet column. Track verified effects separately from failed or uncertain effects. A subsequent save replaces the Undo target; reading the desk does not. Do not chain backwards through older saves.

## Reverse that save

An immediate Undo targets the saved preview, including a partially saved preview's verified effects. Before any write, count each affected record or Calendar event. For more than 3 effects, or a decision requiring the sales lead's or developer's authority, show a one-line Undo preview and ask "Undo?"; wait for a yes and verify the required authority. Smaller undos run immediately. A nurture stop is never reversed: leave its stop history/state and provider cancellation intact, say "Nurture stays stopped," and offer the normal re-enroll flow with its permission and approval checks. If other effects remain to undo, apply the same effect count and authority rule to those effects. Keep the same acting authority and literal-text protections. Re-read the affected rows, effective history and provider event before writing. If somebody changed the same facts since the save, do not overwrite them; ask one plain correction question showing the conflict. An uncertain provider result needs reconciliation before deciding what exists.

1. **History first.** Skip nurture-stop records throughout Undo, including history and current/provider state. Skip task-open records here; they are reversed only by `task_cancelled` in step 3, without a correction to the opening row. For other history, append `record_type=correction` rows linked through `corrects_interaction_id`, with the original channel, the confirmed operator and fresh audit time. Never edit or delete any Interactions row. Use the exact source-key format `undo:<original source_key>:e<n>` for every Undo history row, including task cancellation. `<original source_key>` is the full saved row's source key, unchanged; `<n>` starts at 1 and follows a deterministic order of reversal rows for that source in the receipt. For example, `chat:abc:e1` becomes `undo:chat:abc:e1:e1`. Keep these assignments across retries. Before appending, search for that exact key. If it exists, verify and reuse the row, then finish only missing current-record or Calendar effects; never append another copy. A correction of a correction follows its effective root; restore the values that were effective immediately before the save. Omitted cells do not erase anything: use the existing `clear` sentinel for removed optional values.
2. **Withdraw a new fact.** Skip `task_opened` records entirely in this step: step 3 cancels them only. Also skip nurture stops, which Undo never reverses. When the save added another fact with no predecessor, correct it to `event=note`, summary "Entry taken back by <operator>.", and clear its person/partner/unit links and affected optional fields, including deposit date, next step, attribution and `workflow_json` as applicable. Restore known prior stage/unit-status values; when no prior value exists, the cleared target links withdraw those effects without writing an invalid enum value. Clear identity-merge links too if this save created them. This leaves the raw source and audit trail intact while removing the withdrawn fact from the buyer, transaction or workflow projection. When undoing an edit, restore its previous effective event, links, structured fields and full workflow payload instead. Do not invent a reverse transaction or a new enum.
3. **Current records.** Restore only cells changed by this save, using the recorded before values and fresh effective confirmed history. Current-record cells use their actual prior blank/value, not the history-only `clear` sentinel. Restore an existing task's previous owner, date, status and close metadata. Cancel a newly opened task only by appending a `decision` row with `event=task_cancelled` and reason "Taken back", using the exact Undo key and pre-write duplicate check from step 1. Set the task's cancelled status and close metadata from that verified cancellation row; keep the opening history and task row unchanged otherwise. Do not correct or neutralize its `task_opened` row. Recompute the buyer's earliest open next step through desk-tasks. Reopen Review items this save resolved, clearing only this save's resolution metadata; questions created solely by the withdrawn entry are closed with the Undo correction as their explanation. Keep all Review rows. For People, Partners, Pipeline or Campaigns rows created by the save, retain the row and its internal key, clear only the introduced writable values, and record the withdrawal in history. Never clear manual or formula cells, or a value introduced by another save.
4. **Calendar.** Reverse only this save's event changes on the configured shared task calendar. Delete an event this save created; restore the previous date/time, title, guests, color, description and reminders for an event it updated. If this save deleted an event, restore it through the provider's supported undelete or recreate from the verified prior contents, then update the task's event link if the provider gives a new ID. Preserve the appointment instant and zone. Training omits attendees and sends no notifications, as desk-tasks requires. Do not invite buyers or partners. Check actual provider state before retrying a timeout; never recreate blindly.
5. **Verify.** Read back every correction, changed cell and Calendar event. Deletion needs explicit absence or cancelled status, not an error. Mark the Undo receipt complete only when all required effects verify. A repeated Undo reports that it is already undone, without writing again. If something fails, keep the verified corrections, say the remaining step in plain words and retry only that step after reconciliation. Do not say "Undone" while the Calendar or another required effect is uncertain.

Confirm in one line, for example: "Undone. Nora's call is back on Thursday." No extra approval round after any required Undo? confirmation. Older changes use desk-log's ordinary correction preview. Undo reverses desk records and Calendar effects; it cannot retract a delivered notification or message. Never claim an external send was recalled. A nurture stop remains stopped, including its history and provider state. Undo never restarts it, silently or after confirmation. Offer the normal re-enroll flow instead; a real opt-out still blocks enrollment until its explicit permission requirements are met.
