# Workflow record and execution contract

## History and migration

Add one plain-text column, `workflow_json`, at the end of Interactions and its Schema row. Never shift existing columns or formulas. Existing blank values remain valid. This private workflow payload is excluded from all report snapshots, published reports and the browser's offline cache. Do not put email addresses, message bodies, API tokens or commission terms in it. A readable neutral `summary` accompanies every row.

Each payload has `version:1` and `kind`. It carries only supplied or explicitly confirmed values. Use the source's stable identity and event position. For a new chat workflow use `chat:<uuid>` as the stable source identity, with event-position suffixes on row source keys (`chat:<uuid>:e1`, `:e2`, and so on); keep the same UUID across retries. `dashboard:<operation UUID>` is history only, retained for earlier records, never a source for new writes. The JSON adds structured requirements without replacing the existing `event`, `stage`, `unit_status`, `next_step` and `next_step_due` fields. Apply normal corrections to the entire event. Derive current workflow state from effective history in occurrence order, then the original logged time and row order. A correction's actual logged time stays on its raw audit row; it must not move the original fact after a same-day outcome. Old Interactions rows stay unchanged. Never deduce marketing permission from a blank.

Kinds:

- `buyer`: `stage`, `owner`, `effective_date`, `reason`, `review_date`, `resume_condition`, `next_step`, `task_owner`, `due_date`. Optional task replacement is explicitly confirmed. Write the matching normal stage event, including `on_hold`, `nurture`, `lost`. The Pipeline next step still follows the earliest open task.
- `villa`: `person_id`, `unit_id`, `status` (requested/accepted/release), `reason`, `accepted_by`, `evidence` (neutral description, not raw contract), `starts_at`, `expires_at` (offset timestamps), `terms` (hold terms only), `next_step`, `task_owner`, `due_date`. Map accepted to `hold_accepted`, release to `hold_released`; buyer stage is unaffected.
- `nurture`: `enrollment_id`, `track`, `content_version`, `provider_sequence`, `status`, `confirmed_by`, `reason`, `cancel_required`, `handoff_key`, provider event IDs in `processed`. Status may be pending, active, paused, opted out or needs attention. Store provider references, not message content. Only provider acknowledgement establishes active or cancelled delivery.
- `booking`: `status` (booked/cancelled/completed), `starts_at`, `provider_event_id`, `confirmed_by`. Includes legacy discovery calls, meetings and tours. Log the supplied booking identity once; a cancellation/completion ends that booking path. Use normal `event=note` for a call or meeting booking. New identified tours use `journey` below. A discovery call or meeting booking alone does not advance the buyer to Tour.
- `followup_alert`: `key`, `task_id`, `due_date`, `owner`, `eligible_on`, `status`, optional provider `message_id`. Key is `followup:<task_id>:<confirmed due date>`. Prepared or uncertain attempts must be reconciled before any resend.
- `review_note`: `text`, a concise confirmed answer. This never closes a question by itself.
- `journey`: the confirmed readiness, handoff and individually identified visit events below. The row supplies the buyer identity. Preview the required Tour stage and linked host-task/Calendar effects for a booking in the same confirmation. Other owner, stage, source, consent or villa changes require their own confirmed facts; no event infers them.

Use `require('./scripts/rules.cjs')` from this skill directory to validate buyer, villa and enrollment payloads. `workflows` reads versioned events, `nurture` applies provider events, `alert` calculates eligibility. These helpers do not authorize mutations or replace the confirmation steps.

Website inquiries follow [website-intake.md](website-intake.md). `scripts/intake.cjs` is a pure planner that validates source evidence and prepares proposals without writing to the Sheet or connecting a provider. The website-v1 activation contract is disabled until verified against its evidence gate; email is not a required intermediary.

## Readiness, handoff and visits

Use [tour-checklist.md](tour-checklist.md) for the agreed before-visit preparation, confirmations, coverage, outcome and end-of-day checks. Real message delivery remains unverified until its connected evidence gate passes.

Use `scripts/journey.cjs` as `DeskJourney` in the live dashboard or `require('./scripts/journey.cjs')` in Node. `validate(value, {owners, today, actor, state, now, timeZone})` returns a normalized proposal or an actionable error. `now` is the actual or explicit practice clock instant with offset; `timeZone` is the confirmed appointment/reporting zone. Read fresh effective history and pass `state(rows, person_id, {today, now, timeZone})` before acceptance or a visit update. The module returns `{qualification, handoff, tours, booked, gaps}`; questionable historical outcomes retain their recorded status and get `timing_issue` and a visible `tour_timing` gap. Do not treat that gap as verified completion. `suggestions(state, {today, owner})` returns proposals `{key, task, owner, due_date}`. Stable internal keys identify the underlying visit/event, never the day of a repeated check. Labels do not show IDs. A missing owner or deadline stays blank until explicitly confirmed.

Every journey payload has `version:1`, `kind:'journey'`, `type`, stable `event_id`, valid `effective_date`, and `confirmed_by` matching the authenticated operator and roster. Store neutral supplied facts, never raw messages, contact details or credentials. Supported types:

- `qualification`: `outcome` ready / needs information / not ready / not a fit, `reason`, and boolean `conversation`. Set `conversation:true` only for an actual conversation with the buyer, even when reported later in a voice note. Missing/false means an internal decision for historical compatibility. Capture the buyer and confirmed acquisition source first; an absent readiness decision stays unknown. Show the readiness and any Contact and discovery stage change as explicit confirmed facts. Review known qualification before offering a tour and ask only for consequential missing answers. Do not invent a hard readiness threshold; the exact questionnaire is deferred.
- `handoff_offered`: `handoff_id`, `from_owner`, `to_owner`, `context`. The current buyer owner stays in place until a separately confirmed owner change. A pending acceptance remains with the sender, including when Jorge covers Freddie.
- `handoff_accepted`: `handoff_id`, `accepted_by`. Require the current matching offer and the recipient's authenticated identity. Selecting the recipient's name is not acceptance. Save acceptance and show an explicit buyer-plan owner change separately. Preserve the acceptance date separately from the offer date. Suggest a first personal response by the next Monday–Friday business date after acceptance, with the recipient as proposed task owner and context retained. Friday means Monday; holidays are not modeled. This approved response rule proposes the date for operator review and does not save the task automatically.
- `tour_requested`: `tour_id`, `owner`, `next_step`, `task_owner`, `due_date`. This requests a visit and proposes the supplied action; it does not confirm a booking.
- `tour_booked` / `tour_rescheduled`: `tour_id`, `owner`, `starts_at` with explicit timezone, `preparation` (confirmed checklist or context, which may be blank). Confirmed booking advances `lead`, `contact and discovery` or `presentation` to `tour`; keep later and side-outcome stages intact. Include the stage and owned host-task/Calendar effects in the save preview. Rescheduling requires an existing open booking and updates that visit's same linked task and Calendar event. A new visit after completion, cancellation or no-show needs a new visit identity.
- `tour_preparation`: `tour_id`, nonempty `preparation`. Require an existing open booking. Update only its confirmed checklist or context; its booking time, owner and status stay intact.
- `tour_cancelled` / `tour_no_show`: `tour_id`, `reason`; `tour_completed`: `tour_id`. Completion and no-show may carry `occurred_at`, an actual ISO instant with explicit offset. Require a known confirmed open booking. Completion/no-show cannot precede its scheduled instant or occur after the actual/practice clock. Compare the supplied date/time in the confirmed zone, never the browser's date. Date-only evidence from an earlier appointment-local day rejects; a same-day outcome requires the real time. Later-day date-only evidence is usable if not future. If the visit actually happened earlier than recorded, first confirm and append the appointment correction with evidence, then validate the outcome against it. A generic “yes” never bypasses the guard. Save confirmed completion even if recap or task saving is incomplete. Each outcome affects only that visit; older events cannot reopen a terminal visit. Preserve questionable legacy outcomes visibly for reconciliation.
- `tour_recap`: `tour_id`, natural `recap`, `next_step`, `task_owner`, `due_date`; or `recap`, explicit `no_next_action:true`, and `reason`. Require confirmed completion. Record the supplied recap once. Correct the earlier interaction when revising it; do not invent positive/negative feedback categories or overwrite history.

Project booked/rescheduled to the existing `tour_booked` event and completed to `tour_completed`. Project the other journey types to `note`, with a clear factual summary. A qualification row is `touch` only when `conversation:true`; an internal readiness decision is `decision`. Use `occurred_at` as the outcome timestamp when supplied, otherwise its confirmed date. Use no new Sheet event enum or columns. Validate individual visit identities: a cancelled/completed visit must never cancel another booking. Preserve compatible legacy tour, discovery-call and meeting booking facts; unknown identities/statuses do not establish a new confirmed booking. Legacy anonymous tour and booking histories keep their own compatibility paths, separate from identified visits.

### Linked host work and partial saves

Use `hostTaskKey(person_id, tour_id)` for the host task's stable opening `source_key`: `journey-host:<person_id>:<tour_id>`. `Tasks.opened_interaction_id` links to that opening interaction. `linkedHostTask(interactions, tasks, person_id, tour_id)` follows effective corrections to its original receipt identity; it returns the task (including a closed task) or null when no opening exists. It never matches by wording, owner or due date. Ambiguous/cross-buyer links throw a reconciliation error. A saved opening with no Task throws `HOST_TASK_MISSING`, with `receipt` and original `opened_interaction_id` for recovery; materialize only that missing Task after reconciling, never append another opening.

- Booking: preview and confirm the actual host owner, appointment-local date/time and zone, host task, Calendar event, and any earlier-active-stage change to Tour. If existing work could be the host task, confirm its identity before linking it; never adopt a matching phrase alone.
- Reschedule: update that same linked host task and Calendar event. Changing only a task deadline never establishes a new booking or changes the appointment instant.
- Visit cancellation: close that visit's linked host task with its reason and cancel only its linked Calendar event. Completion closes its linked host task as done. A no-show closes the host episode with its confirmed outcome and prompts for the next owned action; it does not cancel other visits.
- Direct host-task cancellation: ask “Cancel the visit too” or “Cancel only this task,” with Other last. Show the effects in one preview. Task-only leaves the visit booked and surfaces the missing hosting work. Do not silently restore a deliberately cancelled host task on a later check.
- Every active update must resolve or explicitly surface its next action, confirmed owner and date. Reuse existing confirmed work first. Respect closed/lost and explicit no-action decisions with reasons; no blank task is created to satisfy a prompt.

History, Pipeline/current records, Task and Calendar each have their own receipt. Append and read back the confirmed event first, then reconcile the exact previewed effects. Reuse stable event/operation keys and the opening link. A failed or uncertain read is not absence. Retain verified work and report exactly which effect remains, including a missing host task or unverified Calendar update. Reconcile the provider event ID and stored instant before retrying a timed-out Calendar operation; never create a second appointment blindly. Re-read current records before writes. Changing scope, owner, date or task/visit cancellation choice requires a new preview; a retry of the same confirmed effects does not. Only announce the full booking/reschedule/cancellation saved after every required read-back.

End-of-day gaps include readiness not recorded (owner unknown), pending handoff acceptance (sender), missing completed-visit recap (recorded visit owner), questionable visit timing, a booked visit without verified host work, and a saved recap missing an owned dated next action (visit owner). Keep known overdue dates. When adopting a proposal through the buyer plan, allow an overdue date only after fresh state confirms the same stable proposal, task, owner and date; pass that date as validator context `confirmedDueDate`, never as a payload flag. Ordinary editing and rescheduling still require today or later. Use the existing Today semantics for saved tasks, including preparation that must start today. Do not invent reminders, provider schedules or calendar integration. Proposals are labeled not saved; use the existing buyer-plan/task save and readback process to establish the owned next action. Repeated checks reuse the same proposal key.

`workflow_json` remains private to the live workflow. Reports may use supported existing projected facts only. They cannot infer a complete journey or missing recap from absent private payload; show a concise coverage warning where needed. Local fictional tests establish reducer/validation behavior; actual host identity, connected saves, calendar acknowledgements and provider activation remain evidence gates.

## Buyer and villa rules

On hold requires a supplied reason, start date, review date, confirmed buyer owner, next step with its owner and due date, and what would move the buyer forward. Review must be on or after start and today; the next step is due by review. Long-term nurture needs the same managed review strategy, but never implicitly enrolls marketing. Show upcoming reviews with the buyer's next step. A hold on the buyer never reserves a villa.

Lost needs the actual outcome date and reason. Ask a missing reason under desk-log Before I save. Save approves all displayed proposals and effects. Only a skipped question without a proposal records “Reason not provided,” leaves lost_reason blank, and creates the visible logger follow-up under desk-log Questions and follow-ups. Never invent a reason or an empty task. Existing tasks require explicit completion/cancellation; a lost buyer never automatically releases a villa. Closed needs verified transaction evidence and a handoff owner/next step. Reservation, contract and closing changes go through the unit status reporter's evidence. A booked tour never means a completed tour.

A villa request does not affect availability. Acceptance requires the configured unit status reporter's confirmation, buyer and villa, reason, start and future expiry with time zone, agreed hold terms/evidence, and a dated next step with confirmed owner. An operator may record the reporter's verified confirmation in chat; selecting the reporter's name is not evidence. Immediately re-read inventory before acceptance. A competing accepted hold, reservation, contract or sale stops the write. The dashboard is view-only; acceptance happens in authenticated desk chat with the reporter's verified confirmation. Do not automatically release on expiry: open one question for authorized review. A release requires the reporter's actual decision and matching current holder.

## Marketing and connected email

Capture website, ad, email, WhatsApp and referral sources through their existing verified routes. Preserve first channel/date and supplied campaign/UTM values, store later influence as separate touches, and deduplicate the provider message/lead identity. Unknown source remains unknown. Source is not readiness or accepted referral credit. Confirm readiness from behavior and its reason; accepted referral decisions remain with the sales lead and developer.

Unbooked inquiries use an approved configurable invitation, such as the approved short discovery call. Call duration and invitation wording belong to Alix's approved content version; do not hard-code a 15-minute policy. Confirmed bookings receive confirmation/preparation, never another invitation. Tracks: unbooked, booked, second-home, investment, long-term, agent-network and general (unknown intent). Alix approves each version's branded copy, subject, sender, cadence, entry and exit conditions. Do not generate improvised outbound campaign copy. Partner tracks require partner permission and accepted relationship context; do not invent commission protection or payouts.

`nurture_content_library` is a Settings JSON array. Each approved entry has `track`, `version`, `status:approved`, `approved_by`, `approved_at`, `provider_sequence`. The provider's version contains the actual approved copy/cadence. Keep credentials out of Settings. Enrollment is initially a human-confirmed request, `pending`; require current permission=yes, an owner, approved content and the correct booking branch. Do not repeat an active/pending enrollment or reactivate after an opt-out. A new permission grant after an opt-out requires explicit evidence and review, not a toggle.

The established email/marketing provider owns scheduling, sending, delivery, suppression and cancellation. The desk owns confirmed enrollment state, owner, attribution and human response tasks. `runner.cjs` expects durable provider and desk adapters; it is not production connected. A plain Sheet append is not an atomic queue lock. Until an adapter demonstrates durable reservation, deduplication and cancellation, keep provider activation off and use the internal pilot. No replacement Sheet permissions are required.

A verified reply, booking, takeover, opt-out, relevant stage change (On hold, lost, closed or nurture transition), or bounce stops conflicting future messages. Save the stop request before calling cancellation. Confirm queued-send cancellation with the provider; if unverified, show needs attention and alert the operator. Preserve opt-out even if older delivery/enrollment events arrive later. Create one confirmed human-response task per enrollment handoff key for replies/bookings/takeover. Repeated events do not duplicate it. A failed cancellation must not delay surfacing the human handoff. For initial pilot the operator approves this task; future automatic task rules need an explicit approved owner/date strategy.

Test each connected inbox's identity, draft From/Reply-To, received internal test message/reply, then confirmed CRM match/history/task and duplicate-message suppression. Andie's connection does not prove Alix's or the background runner's access. No real buyer emails in the pilot. Sender activation is a separate connection milestone, not another approval of this product scope.

## Missed follow-up to Alix

Two Monday–Friday business dates after the current confirmed task due date, during the existing morning run in the desk's reporting zone (OCN: America/Mexico_City). Monday to Wednesday; Friday to Tuesday. Do not send during a weekend run; pending eligible alerts resume on the next weekday. Holidays are not modeled. Completion/cancellation suppresses the alert. Explicit rescheduling retains original date and reason in history, then uses the new deadline; moving a calendar display to today does not change the deadline. Ownership stays unchanged.

Default `followup_alerts_enabled=no`. Setup verifies the configured sender, Alix recipient and background sender permissions in an internal test before setting yes. `followup_alert_recipient` is an existing confirmed task-owner name, not a guessed address. Resolve the address from the roster. `followup_alert_sender` is the verified connected sender name. Training never sends live alerts, even if the setting is accidentally enabled.

Before sending, claim the durable episode key, then re-read status, owner and deadline. Record prepared, then sent only after a provider message ID reads back. If a request times out, record unknown and reconcile Sent/provider history; never blindly resend. Definitively not-sent failures may retry after reconciliation. The reference adapter must ensure atomic reservation, a sender idempotency key and one runner; missing any of these blocks activation.

Message: buyer, follow-up, owner, original/current due date, last recorded contact, next step and desk link. Say “No follow-up recorded” when channel coverage is incomplete. No commissions or raw source text. Never complete, reassign or advance the buyer because an alert was sent.

## Recovery and acceptance

The Sheet is not transactional. Append the confirmed fact first, verify it, then update current records and tasks. Use the operation key to reconcile partial saves; never rerun a whole plan blindly. On concurrent edits, stop and review the fresh record. Failed reads are failures, not proof a record is absent. Put resolution metadata on Review first, `status=resolved` last. If final verification fails, report the exact uncertain step.

Connected training checks: current operator vs view filter; renamed/duplicate headers; competing edits; retry after a lost response; preserved manual override; buyer hold vs villa availability; expired hold review; lost/closed handoff; enrollment branches; duplicate/reordered provider events; reply cancellation before the next queued send; opt-out suppression; failed delivery; one human task; Monday/Friday alerts; completion just before send; reschedule; duplicate daily run; uncertain sender response; correct authenticated sender/recipient. Browser practice and local tests do not satisfy these checks.
